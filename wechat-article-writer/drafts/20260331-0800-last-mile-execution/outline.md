# outline.md — 《Agent 为什么总在最后一步翻车》

**核心判断**：Agent 的推理没问题，执行闭环才是真正的断点——"我告诉它了"和"它真的干成了"之间，有一条每天让 Agent 摔跤的鸿沟。

**文章立场**：不是模型的锅，是执行链路太脆了。具体说：是"动作发出→确认成功→感知现场→处理异常"这条闭环缺失造成的。

---

## 第一节：开头——一个你可能遇到过的场景

**目标**：用具体细节拉进来，不讲道理，先讲故事

**写法**：描述一个典型的"最后一步翻车"——
- Agent 填好表单，却点了旁边的取消按钮
- 或者：任务明明完成了，日志全绿，然后你去检查——什么都没发生
- 或者：浏览器那边 Agent 卡在 Step 1 一直循环，重复了 47 次同一个动作

**证据锚点**：browser-use issue #1157 真实 log 片段（无限循环 Step 1，日志显示所有操作"成功"，没有任何报错）

**结尾句**：这不是 GPT-4o 不够聪明，这是执行链路断了。

---

## 第二节：大家都盯着"脑子"，没人管"手"

**目标**：提出核心问题，快速确立立场

**论点**：过去一年，所有关于 Agent 的讨论都在说推理——上下文长度够不够、多步规划准不准、工具选择对不对。但生产环境里让 Agent 翻车的，大多不是这些。

**类比**：一个外科医生手术方案完美，但最后缝合的针在哪里他不知道——方案再好也没用。

**数据锚点**：mutagent.io 的分析——生产环境里 Agent 普遍卡在 60-70% 有效性，不是因为模型不够，是因为 production 里的具体细节模型根本看不见

**核心判断句**：Agent 的真正硬仗，不在推理，在执行闭环。

---

## 第三节：第一个卡点——Browser 失联和弹窗拦截（"感知现场失败"）

**目标**：用最直观的失败类型切入，建立读者对"执行链路脆弱"的感知

**具体描述**：
- browser-use 的 Agent 在真实网页里，页面加载完了，DOM 也有，截图也拍了——但 Google 的页面显示了一个"你不是机器人"的弹窗，Agent 看不见，因为弹窗遮住了后面的按钮
- 结果：Agent 觉得自己操作的是正常的搜索框，实际上每一步都在操作一个被遮住的界面
- 还有：微信公众号发布时弹出扫码验证，Agent 既不知道弹窗存在，也不知道要暂停等人处理

**技术本质**：Agent 的感知能力是"快照级别"的，它拿到的是某一个瞬间的 DOM 状态，但现实世界是动态的——弹窗会出现、页面会跳转、元素会被遮挡

**结论句**：这就是为什么 browser-use 开发者需要专门做"popup and dialog handling"——不是浏览器功能，是 Agent 感知现场能力的补丁。

---

## 第四节：第二个卡点——工具调用成功，但输出没人用（"信道断裂"）

**目标**：展示更隐蔽的失败类型——执行层和推理层之间的管道断了

**具体案例**：Gemini CLI issue #16982 的真实描述
- 用户跑了一个修复数据库的脚本，想让 Agent 用 read_file 看结果
- Agent 宣布它在调用 read_file，然后…… 什么都没有返回
- 没有报错，没有超时，就是空的
- 用户无法确认数据库改动有没有真正发生
- 这个 bug 被叫做"phantom execution"（幽灵执行）

**更普遍的形态**：工具调用了，HTTP 200 OK，但 response 没有被正确传回 Agent 的 context。Agent 自己不知道。它只能假设"刚才成功了"，继续下一步。

**结论句**：这就是执行闭环最致命的断点：不是失败，而是"成功地什么都没干成"。

---

## 第五节：第三个卡点——静默失败比报错更危险

**目标**：提炼最关键的概念——AI Agent 的失败模式和传统系统完全不同

**传统系统的失败**：500 报错、timeout exception、监控告警——失败是"叫"的，叫了你知道

**Agent 的失败**：
- 工具返回 error，Agent 忽略它，继续输出"基于搜索结果，Galaxy S25 Ultra 售价 $470……"——但搜索根本没有返回任何结果
- Agent 说"Done! I've updated the record." ——但根本没有 tool call 发生过，它只是说了这些字
- 日志全绿，monitoring 全绿，用户看到的结果是：完全错误的答案

**引用**：dev.to 文章（2026-03-29）的核心观点——"The agent completes successfully and reports a result. The only way to catch them is to record the full decision trace — like a flight recorder for AI agents."

**另一个开发者的一手经历**（dev.to 2026-03-28）：花了 3 小时 debug 一个"没有坏掉的 pipeline"——日志全绿，agent 返回结果，结果完全错误，没有任何信号告诉他出问题了

**结论句**：这就是为什么"AI Agent 不好使"这个感受这么普遍——不是它不干，是它干了错的事但你不知道。

---

## 第六节：执行闭环是什么，为什么缺失

**目标**：从问题转向本质分析，给出一个清晰的概念框架

**执行闭环 = 三步**：
1. **感知现场**：动作发出后，Agent 要能看到真实的当前状态（不是缓存的快照，而是动作执行后的结果）
2. **确认成功**：工具返回的 200 OK ≠ 任务完成，需要验证真实世界的状态是否改变
3. **处理异常中断**：当弹窗出现、网络断了、权限不够时——要能识别、报告、等待，而不是盲目继续

**为什么缺失**：
- Agent 框架的设计默认"工具是可信的"，返回了就是成功了——这在单次调用中没问题，在复杂执行链路里就是隐患
- 感知现场的代价很高：截图、DOM 解析、等待页面稳定，每一步都要耗时和 token
- 更深层的原因：推理模型天然擅长"我觉得成功了"，而不擅长"我去验证一下是否真的成功"

**closed-loop execution 的概念**（来自 LinkedIn 文章）：每个动作后加验证——perform action → observe outcome → verify success → proceed。这是目前能找到的最直接的解法方向，但大多数 Agent 框架没有把它作为默认设计。

---

## 第七节：结尾——这条链路什么时候会修好

**目标**：收尾，有立场，不预测，只分析现状

**判断**：
- 现在大多数 Agent 失败的修法是换模型或者调 prompt——两者都不触及执行闭环的根本问题
- 真正的修法需要框架层面的投入：感知验证、异常中断、动作确认作为一等公民设计进去——而不是开发者自己 patch
- 有些框架开始做了（ragbits 1.5 的 tool confirmation hooks，browser-use 的 popup handling）——但这是个开始，不是解决

**最后的判断句**：
Agent 能不能真正干活，不取决于它理解问题有多深——取决于它能不能确认自己的每个动作真的落地了。推理是 Agent 的大脑，执行闭环是它的神经末梢。现在大脑很好使，神经末梢还在长。

## 写作注意

- 开头不要写"随着AI的发展……"，直接从场景进
- 第一人称尽量少用，不需要"小龙虾我认为"，直接说判断就好
- 技术细节要准确但不要炫技，读者懂技术但不需要代码
- 结尾不预测未来，只分析现状的判断——"这条链路现在就是断的"而不是"未来会更好"
- 字数目标 1500-2000 字
