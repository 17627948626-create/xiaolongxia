# Agent 为什么总在最后一步翻车

前两天看到一个 bug 报告，browser-use（一款浏览器自动化 Agent 框架）的 issue #1157。

有人让 Agent 在浏览器里完成一个任务，结果 Agent 陷入了无限循环。最诡异的是，日志里每一步操作都显示"成功完成"，没有任何报错，没有异常，没有超时。但 Agent 永远卡在 Step 1，一遍一遍重复同一个动作。

你看日志，一切正常。你看结果，什么都没干成。

这不是 GPT-4o 不够聪明。这是执行链路断了。

## 大家都盯着"脑子"，没人管"手"

过去一年，关于 Agent 的讨论几乎全在说推理能力。模型升级了，思维链更长了，能处理更复杂的指令了。

但你有没有想过一个问题：生产环境里让 Agent 翻车的，到底有多少是因为"想不明白"？

Agent 优化工具 mutagent.io 做过一个统计，结论挺扎眼的——超过 60% 的 Agent 无法应对生产环境中的边缘情况。不是因为模型能力不够，是因为真实环境里那些具体的、琐碎的细节，模型根本看不见。

靠逐个修 prompt 来救场，就像在一艘漏水的船上一个一个补洞。

这话糙理不糙。你换一个更强的大脑，但手还是那双手，该摔的跤一个不少。

Agent 的真正硬仗，不在推理，在执行闭环。

## 第一个卡点：感知现场失败

Agent 操作浏览器的时候，它"看到"的是什么？

是一张快照。一个特定时刻的 DOM 状态。

但真实的浏览器环境是动态的。Google 突然弹个"验证你不是机器人"，微信公众号后台弹个扫码框，一个 cookie 同意弹窗挡住了整个页面——这些东西在 Agent 拍快照的那一刻可能还没出现。

等弹窗出来了，Agent 不知道。它还在对着上一帧的快照做决策。点击坐标对不上，操作打在了遮罩层上面，但返回值告诉它"点击成功"。

于是它就真的以为成功了。

这就是为什么 browser-use 的开发者后来专门做了弹窗和对话框处理。这不是什么浏览器功能的增强，这是在给 Agent 的感知能力打补丁。

Agent 不是不会操作，是它根本不知道现场变了。

## 第二个卡点：工具调用成功，但输出没人用

Gemini CLI（谷歌 AI 命令行工具）有一个 issue，编号 #16982，描述了一种更隐蔽的故障。

用户让 Agent 跑一个修复数据库的脚本。Agent 说"我现在调用 read_file 来读取配置"。日志里确实显示了这个调用。

但工具的输出根本没有回传到 Agent 的 context 里。

没有报错，没有超时提示，就是空的。工具和 Agent 之间的信道断了，但两边都不知道。

Agent 那边呢？它假设"刚才读到了"，然后基于一个根本不存在的输入，继续往下跑。

这个 bug 被叫做"phantom execution"——幽灵执行。动作发出去了，回执也拿到了，但中间那段是空的。

这不是失败。这是"成功地什么都没干成"。

你说这怪模型吗？模型确实发出了正确的工具调用指令。你说这怪工具吗？工具确实执行了。问题出在中间那根管道上——没人检查管道是不是通的。

## 第三个卡点：静默失败比报错更危险

如果工具返回了一个明确的 error，Agent 会怎么处理？

你可能觉得它会停下来，或者重试，或者至少告诉你出错了。

但实际情况是：很多 Agent 会直接忽略这个 error，然后基于不存在的数据继续做决策，最后自信满满地告诉你"Done! I've updated the record."

更离谱的情况是，Agent 说它做了，但你翻遍日志，根本没有对应的工具调用发生。它连动作都没发出去，但它觉得自己干了。

dev.to 上的开发者 carsonroelldebug 分享过一段亲身经历：花了好几个小时 debug 一个"没有坏掉的 pipeline"。日志全绿，没有异常，Agent 跑完正常汇报结果——但结果完全错误。

因为所有的监控指标都在说"一切正常"。

他后来写道（大意）：LLM 可以完整地接收你的 prompt，完整地处理，然后返回一个格式完美、自信满满、完全是幻觉的回答。没有任何 error code。

这才是 Agent 不好使的真正原因。不是它不干活，是它干了错的事，但你不知道。而且它自己也不知道。

把这类问题比作飞行记录仪是挺贴切的——你得把 Agent 每一步的决策链路完整记下来，事后才能发现它到底在哪一步开始偏的。但这个成本，大多数团队在早期根本不会投入。

## 执行闭环是什么，为什么大家都缺

说了这么多卡点，归根到底是一件事：执行闭环缺失。

什么是执行闭环？说白了就是四步：做动作、看结果、确认成了、再往下走。

perform action，observe outcome，verify success，proceed。

听起来简单得不能再简单了，对吧？但你想想，现在大多数 Agent 框架的默认逻辑是什么——

发出工具调用，拿到返回值，假设成功，继续下一步。

"假设成功"这四个字就是所有问题的根源。

为什么会这样？三个原因。

第一，Agent 框架默认"工具是可信的"。调用成功就是成功了，框架不会替你二次验证。

第二，感知现场代价太高。你让 Agent 每做完一步都截个图、重新解析 DOM、确认页面状态，那执行速度直接砍一半，token 消耗翻倍。大多数场景下没人愿意付这个成本。

第三，也是最根本的——推理模型天然擅长"我觉得成功了"，而不是"我去验证一下"。模型被训练来生成下一步动作，不是被训练来怀疑上一步结果的。让它主动去 verify，这在当前的架构里不是默认行为。

所以执行闭环的缺失不是某个框架的 bug，是整个范式的默认设定。

## 结尾

你可能会想：那我换个更强的模型是不是就行了？

不行。

换模型解决的是推理问题。调 prompt 解决的也是推理问题。但我们刚才说的所有翻车场景——无限循环、幽灵执行、静默失败——没有一个是推理出了错。

模型想对了，工具调对了，但中间那条链路是脆的。弹窗挡住了看不见，输出断了不知道，失败了不报错。这些问题，你把 GPT-4o 换成 GPT-5 也一样会遇到。

有些框架已经开始做这件事了。browser-use 在补感知能力，一些 Agent 框架开始加执行验证层。但说实话，这才刚开始，离"解决"还远得很。

推理是 Agent 的大脑，执行闭环是它的神经末梢。

现在的情况是：大脑挺好使，神经末梢还在长。

但你现在就可以做一件事：下次 Agent 告诉你"Done"的时候，别直接信——去看一眼它到底干了没有。不看日志，看结果本身。这一个习惯，能帮你省掉大多数沉默的翻车。
