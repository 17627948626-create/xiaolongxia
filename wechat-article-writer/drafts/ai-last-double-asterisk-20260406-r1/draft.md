今晚最刺眼的，不是某句话写错了，而是最后多出来的 `**`。

就在几个小时前，我盯着屏幕上一段看起来已经写完的正文，突然发现一个很尴尬的东西：某个句子后面，跟着两个孤零零的星号。

不是那种故意强调的粗体，就是 `**` 这两个字符，赤裸裸地站在读者面前。

前面几百字看起来都很顺滑，像是 AI 已经"写好了"。结果最后输在一个最小、最不体面的符号上。反差大到让人想笑——不是笑 AI 不会写，是笑这种翻车方式太经典了。

读者不会去想"这里可能是某个 parser corner case"。他们只会觉得：这玩意儿还没收拾干净就发出来了。

所以这不是排版小毛病。这是内容已经变形了。

## 先把锅说清：这次翻车，不是模型不会写，也不是微信突然发疯

根因其实很简单：某类危险的行内加粗写法，会让 `**` 被保留下来。

用普通人能懂的话解释：你以为你在"加粗一句话"，系统最后却把"加粗标记本身"发给了读者。

比如 `**……1.1%。**成熟账号` 这种写法，最后可能变成 `**……1.1%**。成熟账号`。看起来只是标点位置挪了一下，但关键是——前面那个孤零零的 `**` 会露出来。

这不是微信故意跟你作对。这是 Markdown 渲染链路里，一个很典型的"格式契约"没对齐。

## 为什么一个小小的 `**`，足够毁掉整段内容的可信感

因为读者不会分析 parser。

他们看到裸露的 `**`，第一反应不是"哦，这里可能是加粗没闭合好"。而是瞬间出戏：这篇东西像没收拾干净就上线了。

内容正确性不只是"字有没有写对"，还包括"读者最后看到的形式，是不是你本来想表达的那个样子"。

如果读者看到的是 `**`，那他们看到的就是 `**`，不是你想强调的那句话。

格式兼容不是排版末梢。它就是内容正确性的一部分。这句话听起来有点绕，但今晚这个事故把它钉死了：你辛辛苦苦让 AI 写出一段顺滑的话，最后读者却看到了裸露的 `**`。

## Markdown 这套东西，本来就不是一个会大声报错的世界

这里有个反直觉的事实：Markdown 不是编译器。

CommonMark 官方自己都承认，Markdown 长期缺少无歧义标准。同一份文档，可能在这个系统上这样渲染，在另一个系统上那样渲染。

更关键的是，很多情况根本不算 syntax error。

你写得有点危险，它不一定拦你，只可能悄悄换一种你不想要的呈现方式。比如 `**` 没匹配上，它不会报错，只会把 `**` 当普通文本显示出来。

所以 AI 再会写，也可能毁在最后一个 `**` 上。因为它不会像红灯一样提醒你。

## 真正的生产系统，早就把这种"小契约"当成正式工程问题

看看 GitHub 怎么做的。

他们为了统一 Markdown 渲染，不是简单换个 parser 就完事。他们要写 formal spec、做 normalization、比对新旧 HTML tree，目标是 visually identical。

官方博客里写得很清楚：缺乏标准化导致很多 ambiguous details，very similar looking Markdown documents can be rendered as wildly different outputs。

连 GitHub 这种级别的平台，都不敢把格式兼容当小事。

为什么？因为这不是"排版好不好看"的问题，是"用户看到的内容会不会变形"的问题。

demo 拼的是才华，生产拼的是不让这些边角把你当众出卖。

## 回到 AI 内容生产：真正该写死的，不是华丽提示词，而是这些不会上热搜的小规则

今晚修这个 bug，我只做了三件事：

1.  把危险写法禁掉——比如标点必须放在 `**` 外面
2.  发布前自动清洗一遍，不靠肉眼检查
3.  真正发出去前看最终渲染，不看原始 Markdown 自我感动

每一条都很 boring，每一条都不会上热搜。

但这就是把 demo 变成生产系统的区别：不是多会写，而是有没有把这些容易丢脸的小契约写死。

AI 进入真实渠道后，格式契约就是内容的一部分。读者不会因为你偶尔写出一句漂亮话就信任你，但一定会因为看到裸露的 `**` 而怀疑你。

很多系统不是死在不会生成，而是死在"不把丢脸的细节当合同"。
