今晚最刺眼的，不是某句话写错了，而是**最后多出来的** `**`。

就在几个小时前，我盯着屏幕上一段看起来已经写完的正文，突然发现一个很尴尬的东西：某个句子后面，跟着两个孤零零的星号。

不是那种故意强调的粗体，就是 `**` 这两个字符，**赤裸裸地站在读者面前**。

前面几百字看着都挺顺，像是 AI 已经“写完了”。

结果最后翻在一个最小、也最不体面的符号上。

这个反差甚至有点好笑。不是笑 AI 不会写，是这种翻车方式**太典型了**。

读者不会去想“这里可能是某个 parser corner case”。

他们只会觉得：**这东西还没收拾干净就发出来了**。

所以这不是排版小毛病。

它已经在**改写内容本身**。

---

## 先把锅说清：这次翻车，不是模型不会写，也不是微信突然发疯

根因其实很简单：某类危险的行内加粗写法，会让 `**` **被保留下来**。

用普通人能懂的话解释：你以为你在“加粗一句话”，系统最后却把**“加粗标记本身”**发给了读者。

比如 `**……1.1%。**成熟账号` 这种写法，最后可能变成 `**……1.1%**。成熟账号`。

看起来只是标点换了个位置，但**关键在于**——前面那个孤零零的 `**` 会直接露出来。

这不是微信故意跟你作对，而是 Markdown 渲染链路里一个很典型的**“格式契约”没对齐**。

---

## 为什么一个小小的 `**`，足够毁掉整段内容的可信感

因为**读者不会分析 parser**。

他们看到裸露的 `**`，第一反应不是“哦，这里可能是加粗没闭合好”。

而是瞬间出戏：**这篇东西像没收拾干净就上线了**。

我举个更具体的场景：想象你是一个读者，正在认真看一篇讲 AI 写作的文章。

前面讲得头头是道，你都快被说服了。

突然看到 `**` 这两个字符，脑子里瞬间闪过一个念头：“作者自己都没检查完就发出来了，我为什么要信他说的？”

内容正确性不只是字有没有写对，还包括读者最后看到的形式，是不是你原本要表达的**那个样子**。

如果读者看到的是 `**`，那他们看到的就是 `**`，不是你想强调的**那句话**。

格式兼容不是排版末梢，它就是**内容正确性的一部分**。

今晚这个事故把这件事钉得很死：你辛辛苦苦让 AI 写出一段顺滑的话，最后读者却**只记住了**一个裸露的 `**`。

## Markdown 这套东西，本来就不是一个会大声报错的世界

这里有个反直觉的事实：**Markdown 不是编译器**。

CommonMark 官方在首页就写得很清楚：约翰·格鲁伯（John Gruber）对 Markdown 的经典语法描述，并没有把语法定义得无歧义。

因为没有 unambiguous spec，不同实现已经明显分化；同一份文档，可能在一个系统上这样渲染，在另一个系统上**那样渲染**。

更关键的是，CommonMark 规范里有一句话：“任何字符序列都是有效的 CommonMark 文档。”

这意味着很多格式问题不会像编译错误那样直接把你拦下——你写得有点危险，它不一定报错，只是悄悄换成一种你**不想要的呈现方式**。

CommonMark 官方教程写得明明白白：“The same character must be used to open and close emphasis.”

（强调标记必须用同一种字符打开和关闭；斜体、粗体都适用）。

想让 `*` 作为普通字符显示出来，必须用反斜杠**转义**。

但麻烦就在这儿：`**` 一旦没匹配上，它不会提醒你，只会把 `**` **当普通文本显示出来**。

所以 AI 再会写，也可能毁在最后一个 `**` 上。

因为这里**没有红灯**。

---

## 真正的生产系统，早就把这种“小契约”当成正式工程问题

看看代码托管平台 GitHub **怎么做的**。

他们在 2017 年 3 月 14 日的官方博客文章《GitHub 风格 Markdown 的正式规范》（A formal spec for GitHub Flavored Markdown）里写得很直白：缺乏标准化导致很多 ambiguous details，very similar looking Markdown documents can be rendered as wildly different outputs。

连 GitHub 这种级别的平台，都不敢把**格式兼容当小事**。

他们为了统一 Markdown 渲染，不是简单换个 parser 就算了。

他们要写 formal spec、做 normalization、比对新旧 HTML tree，目标是 visually identical；而且还特别强调**user data was never destroyed**。

最硬核的是，GitHub 当时统计过，受影响的文档其实不到 1%。

但即使是这么小的比例，他们仍然认为这是大规模内容、真实用户会遇到的问题，必须当成**正经工程来处理**。

为什么？因为这不是“排版好不好看”的问题，而是“用户看到的内容会不会**变形**”的问题。

demo 拼的是才华，生产拼的是**别让这些边角在公开场合把你出卖**。

---

## AI 写作系统最脆弱的，不是生成那一层，而是最后一跳的契约传递

这才是今晚事故暴露出来的**真正痛点**。

很多人以为 AI 内容生产的难点，是“让模型写出好句子”。

但更隐蔽、也更容易丢脸的是：那些好句子离开模型之后，还要经过 Markdown、解析器、富文本转换和平台渲染。

每一跳，都可能让内容**变形**。

`**` 泄漏不是模型写错了，是**最后一跳的契约没对齐**。

你让 AI 写“`**冷启动期接近于零。**不是很低`”，它写对了。

但到了渲染器那里，它可能变成“`**冷启动期接近于零**。不是很低`”，然后把 `**` 露给读者。

这不是生成问题，是**传递问题**。

很多系统不是死在不会生成，而是死在没有把这些最容易丢脸的**细节当合同**。

---

## 回到 AI 内容生产：真正该写死的，不是华丽提示词，而是这些不会上热搜的小规则

今晚修这个 bug，我只做了三件事：

1. 把**危险写法禁掉**——比如标点必须放在 `**` 外面
2. 发布前自动清洗一遍，不靠**肉眼检查**
3. 真正发出去前看最终渲染，不看原始 Markdown **自我感动**

每一条都很 boring，也都**不会上热搜**。

但这就是 demo 和生产系统的分水岭：不是你多会写，而是你有没有把这些最容易丢脸的**小契约写死**。

本地这次也不是抽象理论，而是已经落成了双保险：layout prompt 里明确禁止危险写法，normalize 脚本在发布前**兜底清洗**。

两层一起上，才算真把“最后一个 `**`”这种事故**挡在门外**。

AI 进入真实渠道后，格式契约就是**内容的一部分**。

读者不会因为你偶尔写出一句漂亮话就信任你，但一定会因为看到裸露的 `**` 而开始怀疑你。

很多系统不是死在不会生成，而是死在连最丢脸的细节都**没当合同**。
