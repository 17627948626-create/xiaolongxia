# 选定论点

**今晚这次 `**` 泄漏说明，AI 内容生产里最容易丢脸的，往往不是模型不会写，而是输出经过 Markdown、渲染器和发布平台时，那些没人当回事的小格式契约没有被写死。格式兼容不是排版末梢，而是内容正确性本身。**

# 结构提纲（7 节）

## 1. 开头：今晚最刺眼的，不是某句话写错了，而是最后多出来的 `**`
- 直接从事故瞬间写起：正文本来很顺，结果读者眼前突然裸露出一个 `**`
- 点明反差：前面看起来像 AI 已经“写好了”，最后却输在一个最小、最不体面的符号上
- 前 300 字就下判断：**这不是排版小毛病，这是内容已经变形了**

## 2. 先把锅说清：这次翻车，不是模型不会写，也不是微信突然发疯
- 交代真实根因：某类危险行内加粗写法会让 `**` 被保留下来
- 用普通人能懂的话解释：你以为你在“加粗一句话”，系统最后却把“加粗标记本身”发给了读者
- 可以点一个最小例子，但不要铺太多技术细节

## 3. 主判断：为什么一个小小的 `**`，足够毁掉整段内容的可信感
- 读者不会分析 parser，只会瞬间出戏：这篇东西像没收拾干净就上线了
- 内容正确性不只是“字有没有写对”，还包括“读者最后看到的形式是不是你本来想表达的那个样子”
- **这里要把“格式兼容=内容正确性的一部分”钉死**

## 4. 支撑洞察一：Markdown 这套东西，本来就不是一个会大声报错的世界
- 引 CommonMark 官方两点：Markdown 长期缺少无歧义标准；很多情况根本不算 syntax error
- 解释成大白话：它不是编译器，你写得有点危险，它不一定拦你，只可能悄悄换一种你不想要的呈现方式
- 回扣标题：所以 AI 再会写，也可能毁在最后一个 `**` 上，因为它不会像红灯一样提醒你

## 5. 支撑洞察二：真正的生产系统，早就把这种“小契约”当成正式工程问题
- 引 GitHub 的例子：为了统一 Markdown 渲染，要写 formal spec、做 normalization、比对新旧 HTML tree
- 重点不是讲 GitHub 多厉害，而是讲一个直觉：**连这种级别的平台，都不敢把格式兼容当小事**
- 落一句狠判断：demo 拼的是才华，生产拼的是不让这些边角把你当众出卖

## 6. 回到 AI 内容生产：真正该写死的，不是华丽提示词，而是这些不会上热搜的小规则
- 提 3 条就够，不要扩成清单文：
  1. 只允许安全子集写法（比如标点放在 `**` 外）
  2. 发布前自动做 normalization，不靠肉眼
  3. 真正发出去前看最终渲染，不看原始 Markdown 自我感动
- 这一节的作用是把文章从“吐槽事故”抬成“有判断的经验”

## 7. 结尾：把 demo 变成生产，不是多会写，而是不让最后一个 `**` 出现在读者面前
- 收束到一句更大的判断：AI 进入真实渠道后，格式契约就是内容的一部分
- 回应开头：真正让人信任的，不是它偶尔写出一句漂亮话，而是它在最后一步也不露馅
- 结尾建议短、硬、像拍桌子：**很多系统不是死在不会生成，而是死在“不把丢脸的细节当合同”。**

# 写作提醒
- 全文只讲这一件事，不展开成泛泛的“可靠性”大题目
- 不要重复最近那篇“最值钱的不是模型”的结构和措辞
- 技术词最多点到为止，每次都要翻译成读者感受：出戏、掉信任、像半成品
- 标题和开头必须强呼应：标题里的“最后一个 `**`”在前两段就要出现
