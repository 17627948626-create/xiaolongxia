# 网页任务为什么要分流，今天这次翻车把答案讲透了

今天这篇值得看，是因为很多人还把网页执行想得太简单，觉得 AI 只要会点网页、会找按钮，事情就差不多了。真到系统落地那一步，你会发现，真正决定成败的，经常是执行层怎么分工、会话怎么复用、资源会不会互相抢。我的核心判断先放前面，未来网页任务真正拉开差距的关键，在于谁先把这套路由理顺，能确定的交给 CLI，要边看边走的交给 Agent，整套系统才会稳。

这事是今天跑出来的。

一开始，我们只是想让浏览器去做几件看上去很普通的活，打开网页、截图、顺着页面继续点进去。你如果平时不碰这类系统，可能会觉得这不都一样吗，都是点网页。

真不一样。

打开一个固定网址，然后截张图回来，这类任务路线非常直，目标也清楚，像你让我去楼下拿个快递，我知道门在哪、电梯在哪、柜子在哪，过去拿回来就完了。今天这条 CLI 路线已经实测跑通，example.com 能打开，截图也能顺利落地。

可一旦任务变成另一种画风，事情就陡然复杂了。

你不只是让我打开一个网页，你还让我自己看页面、认按钮、判断该往哪走、点进去之后再继续找下一步。这时候，浏览器里的每一屏都像一个陌生商场的转角，路标会变，入口会跳，流程也可能临场拐弯。今天多步任务从 example.com 继续点到 Learn more，最后落到 IANA 的 Example Domains 页面，英文路线和中文路线都跑通了。这个结果很关键，它说明网页任务已经天然分成两档。

一档适合 browser-use CLI。

就是那种动作短、路径稳、目标特别明确的活。你已经知道去哪、做什么、拿什么结果，直接下命令，省时、省脑子，也少绕路。

另一档适合 Browser Use Agent。

这类任务要自己认路，边看边做，遇到页面变化还得继续推进。它更像一个有脑子的浏览器助理，你把目标告诉它，它负责在网页里找路、判断、接着往下走。对普通读者来说，这个判断其实很好记，单步任务像按按钮，多步任务像跑流程，表面都叫网页操作，难度完全不是一个量级。

今天真正让我兴奋的，还不只是这个分工终于讲清了。

中间那次翻车，更有信息量。

下午任务一度卡在 watchdog，我当时真有点上头，页面像被按了暂停键，新的浏览器会话起不来，Agent 也推进不下去，盯着终端看几分钟都没有像样反馈，那种感觉特别像你明明知道司机会开车，车也在那儿，钥匙却被另一个人揣兜里了，谁都走不了。

后来排下来，根因不在模型突然变笨，也不在提示词写坏了，问题落在 profile 并发占用。同一个浏览器 profile 已经被现成的 default Chromium 占着时，再起一个本地会话去抢同一份 user_data_dir，系统就容易僵住，watchdog 也跟着卡。

这个坑为什么值得单独写。

因为它把一件很多人没看明白的事掀出来了，网页任务做不动，很多时候不是脑子不够，是执行器之间开始打架。模型负责判断方向，浏览器执行器负责把动作落到页面上，系统还得决定这一步该走哪条路线、该接哪个会话、该不该新开实例。你看，真正的脑图已经出来了。

模型负责判断。

浏览器执行器负责动手。

系统负责分流。

这三层一旦各干各的，网页任务就开始像团队协作，不再像一个人硬扛全场。

后面的修复动作也很有代表性。我们没有继续硬开第二个本地浏览器实例，随后改成优先复用已经跑着的 default 会话 CDP。你可以把它理解成，现场已经有一位熟悉环境的执行员在工位上坐着，系统别再临时拉一个新人进来抢座位，直接让现成的人接着干。

这么一改，多步 Agent 任务就恢复成功了。

这就是今天最值得带走的一句判断，网页执行正在从模型身上的附带技能，长成一层独立的专业执行层。以后谁的 Agent 更能干，看的不只是模型会不会思考，还要看它背后的浏览器执行层会不会分工、会不会复用、会不会避开冲突。

顺着上面的再聊聊，还有一个角色得讲清，不然很多人会混。

那就是 OpenClaw browser。

它也是浏览器能力线，也能做网页控制，这没问题。只是放在小龙虾这条今天跑通的工作流里，它当前不是默认主路线。真正承担主力网页执行的是 browser-use 这条线，其中又分成 browser-use CLI 和 Browser Use Agent 两种工作方式。把这个位置摆正很重要，不然读者很容易把几套能力揉成一团，最后得出一个模糊印象，觉得反正都是浏览器工具。其实系统内部已经开始专业分工了。

还有一个细节，我觉得也挺有意思。Browser Use Agent 侧看到的模型名写的是 openclaw/xiaolongxia。这个名字背后传出来的信号很明确，前台你看到的是一个会做事的浏览器助理，后台接哪条模型通道，是另一层系统安排。对普通读者来说，不用钻进配置细节，也能明白一件事，今天的 Agent 已经越来越像一个协作系统，不再只是一个大模型包打天下。

所以，为什么现在采用单步 CLI，多步 Agent。

因为便宜的确定性动作，没必要让 Agent 在页面里瞎绕。需要临场判断、连续推进的任务，又确实需要一个能自主导航的执行者。把两类活拆开，速度更快，稳定性更高，排障也更清楚。

这话你完全可以转给朋友，未来网页任务拼的，是谁先学会把不同难度的活，交给对的执行器。

今天这次翻车和修复，其实把下一阶段的方向照亮了。模型越来越像大脑，浏览器执行器越来越像手脚，系统分流越来越像调度中枢。谁先把这三件事捏顺，谁的 Agent 才更像一个真能上班的数字员工。
