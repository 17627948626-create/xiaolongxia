## 今晚流程经验补充

- 首轮 research 失败的真实原因不是题目或 prompt，而是 **researcher 子任务启动瞬间撞上 gateway draining / restart**；表现为 `researcher_failed_gateway_drain`、无 `research.json` / `outline.md`、子任务几乎未真正开始。以后看到这类失败，要先判断是不是运行时拒单，不要误当成研究质量问题。
- 这类 `researcher_failed_gateway_drain` 的正确处置是：**主 agent 读取 completion event + 失败草稿 `pipeline-state.json` 确认根因后，整轮 fresh rerun Orchestrator**；不要主 agent 自己手写 research / draft 去硬接管整条流水线。
- 今晚最终文章的模型分工已确认：**Writer 初稿与 3 轮改稿都是 `deepseek/deepseek-chat`；但 `final.md`（humanizer）和 `final-layout.md`（layout）是 `openai-codex/gpt-5.4` 产出**。如果老板以后觉得“明明设了 DeepSeek，成品却像 GPT”，优先怀疑的是后处理环节的文风覆盖，而不是 Writer 没切成功。
- Humanizer 今晚主要做的是：去说明书味、把书面/翻译腔磨顺、统一中文语气和节奏、把判断说得更像观点文；它没有重写核心 thesis，但会显著改变最终成稿的“口气”。

## 选题流程再迭代（实现方案一）

- 为解决“先定题、后进 forge 搜资讯”的顺序矛盾，主流程从 2026-04-06 晚起改为：**主 agent 先做热点预扫（2–3 个候选）→ 选题 → 再跑 forge**。
- 热点预扫由主 agent 负责，默认用 `jj-search-stack`，必要时 `tavily-search` 补充；目标不是直接写，而是先摸清最近 24–72 小时 AI 圈最值得借的入口。
- 预扫输出的最小结构固定为：`event / keywords / why-now / thesis-seed`。之后 Orchestrator/Researcher 以此为起点做验证、补证、收口，而不是从零重新决定今晚写什么。
- 已同步修改：`AGENTS.md`（主流程）、`wechat-article-forge/SKILL.md`（caller-precheck override）、`references/researcher-prompt.md`（respect parent precheck）。

## 今晚第二轮系统收口（权限 / 重试 / 文风）

- 选题权限边界已写死：主 agent 有第一选题权；Orchestrator 只有流程权；Researcher 只有验证 + 有限纠偏权；Writer / Humanizer / Layout 无改题权
- Researcher 启动级故障已单独归类为“可重试运行时错误”：命中 `GatewayDrainingError` / `task not accepted` / 启动前拒单时，先做 3s / 8s / 15s 退避重试，并在 `pipeline-state.json` 记录 `researcher_spawn_retry_count` 与 `last_spawn_error_kind`
- 新增 `references/humanizer-prompt.md`，把 Humanizer 边界写硬：只能清理 AI 味和顺节奏，不能覆盖 Writer 的基础文风，更不能抹平成 generic GPT 腔
- `references/layout-prompt.md` 已补强：Layout 明确没有文风权，不能借“格式化”继续改措辞或语气
- `references/writer-prompt.md` 已补强：Writer 被定义为文章基础声音的拥有者，下游只能润色，不能抹平
- 老板新增风格点名：文章里高频出现“不是……而是……”像 AI 套句。已按“只改一处”的思路，直接加强 `references/humanizer-prompt.md`：把 `不是……而是……` / `这不是……而是……` / `不是 X，而是 Y` 列为高优先级清理对象，要求 Humanizer 默认主动打散这类句式
- 同时补了 Humanizer 的量化边界：**单次实质改动上限 6 句**。目的是防止 Humanizer 从“去 AI 味 + 顺节奏”滑成“半重写”，继续覆盖 Writer 的基础文风
