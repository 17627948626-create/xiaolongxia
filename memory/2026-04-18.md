- 从今天起，`browser-use` 分成两档：
  - **确定性网页操作** → 优先 `browser-use` CLI
  - **不确定性、多步、自主导航网页任务** → 默认切 Browser Use Agent 模式

  - 如果明显属于不确定性网页任务，不再反问要不要 Browser Use Agent，直接无感切过去
- 反例边界也已明确：
  - 老板只说“打开这个网址” → 默认走 browser-use CLI；这是确定性单步操作
  - “去后台看一下数据，顺便点进去导出来” → 默认走 Browser Use Agent；这是不确定性、多步、自主导航任务
  - “把当前页面截个图发我” → 默认走 browser-use CLI；这是确定性页面操作
  - “登录后帮我把这几个步骤跑完” → 默认走 Browser Use Agent；登录后流程通常有分支和页面判断
- 三层角色必须分清：
  - `browser-use CLI`：确定性、命令式浏览器操作层
  - `Browser Use Agent`：不确定性、多步、自主导航的浏览器智能执行层
  - `OpenClaw browser`：OpenClaw 自带浏览器控制工具，当前不是小龙虾同类网页任务的默认主路线
- 红线重述：
  - 小龙虾自己的浏览器任务默认不要乱切 OpenClaw browser，除非有明确特殊原因
  - Browser Use 侧不要把 model 直接写成 `openai-codex/gpt-5.4`，正式写法是 `openclaw/xiaolongxia`
- 若 Browser Use Python 路线再卡 watchdog，第一优先排查：
  1. `BrowserSession` 是否显式传了 `is_local=True`
  2. `user_data_dir` 是否确实是 `/root/.config/browser-use-profiles/xiaolongxia`
  3. 是否保持了 `chromium_sandbox=False`
  4. 是否有旧 daemon / 错误 profile 绑定抢占，尤其误落到 `/root/.config/browser-use-persistent`
- 若 `browser-task` 与旧 CLI wrapper 行为不一致，优先相信 `browser-task`，因为它是当前统一入口和默认分流口径所在，旧 wrapper 只是一条兼容/底层执行路径
- 以后收到网页任务时的默认判断顺序：
  1. 先判断任务是确定性单步，还是不确定性/多步/自主导航
  2. 能走统一入口就先走 `/root/.openclaw/workspace-xiaolongxia/scripts/browser-task`
  3. 确定性任务保留 CLI；不确定性/多步任务切 Agent
  4. 若执行异常，再回查 `is_local=True` / `user_data_dir` / `chromium_sandbox=False` / 旧 daemon 占错 profile
- 使用习惯口径：
  - 只要是正常浏览器任务，优先直接走 `browser-task`，不要现场重新拼 browser-use 命令或 Python
  - 只有在调试底层、修脚本、或明确要绕过路由验证某一层行为时，才直接手写 CLI / Python
- 2026-04-18 下午排障补充：新一轮实测里，CLI 路线（打开页面、截图）通过，但 Agent 路线一开始连续卡在 browser start watchdog。最终定位到一个关键并发约束：**同一个 `user_data_dir=/root/.config/browser-use-profiles/xiaolongxia` 如果已经被现成的 default Chromium 占着，Python `BrowserSession(is_local=True, ...)` 再起本地浏览器时会一起卡住 watchdog**。证据链：1) `browser_use_openclaw_agent.py` 参数本身无误，`is_local=True` / `chromium_sandbox=False` / `user_data_dir` 都已正确传入；2) profile guard 显示当前 `default` session 的 Chromium 正在持有该目录；3) 在占用状态下，最小 `BrowserSession.start()` smoke test 也会卡 watchdog；4) 执行 `browser-use close` 释放现有持有后，同样的最小 smoke test 立即成功启动并正常 stop。当前结论：Agent 路线的这次失败，根因优先级应判为**同 profile 并发占用冲突**，不是 LLM/base_url/model 配置错误。后续若要稳定共存，要么先复用现有会话，要么在 Agent 路线上改成单独 profile / session 策略，至少不能默认与现成 default Chromium 同时各自抢同一 `user_data_dir`。
