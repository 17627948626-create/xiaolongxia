# 规则源与活配置收口方案（最小可实施版）

日期：2026-04-15
角色：方案调查员 C（规则源 / 活配置收口）
范围：只看现行规则源是否还有执行歧义口子；不做实现，不改文件。

---

## 先说结论

今晚关于 Writer backend 的主口径，已经基本收住了：

- Writer / Revise = **spawn 子 agent**
- 默认 **继承主模型**
- `writer_model` = **可选 override**，为空则不覆盖
- 每轮 revise = **必须新 spawn 独立 Writer 子 agent**
- review 通过线 = **只认 `config.json.review_pass_threshold`**

现阶段真正还会复发歧义的，不是“旧 backend 还在不在”，而是：

1. **临时 run 放行** 和 **长期默认配置** 还没有彻底分轨
2. **哪些文件是活规则源，哪些只是记忆/说明**，还没被一句话钉死
3. `writer_model` 虽然语义已经收窄，但**“空字符串=继承父级模型”** 还缺一个更硬的合同化表述

所以这轮最小修复，不是再大改规则，而是把“单一权威源 + 例外走专门通道”写死。

## 一、现行规则源状态：哪里已经收口，哪里还留口子

### 已经收口的部分

从本次检查材料看，以下几条已经在活规则源里基本一致：

- `AGENTS.md` 已写明：
  - 通过线数字不再写死在 AGENTS，唯一权威源是 `wechat-article-writer/config.json.review_pass_threshold`
  - 旧 Writer backend 全部退出当前产品面
  - Writer / Revise 改为 spawn 子 agent，默认继承主模型
  - 每轮 revise 都必须重新 spawn 一个新的独立 Writer 子 agent
- `USER.md` 与上述口径一致
- forge `SKILL.md` 与上述口径一致，且已经把：
  - `writer_model` 收为 optional override only
  - Step 2 / Step 4 默认继承父级模型
  - revise 每轮新 spawn 独立 Writer
  - 通过线只认 config
  写进去了
- `config.json` 当前值已经是：
  - `review_pass_threshold = 7.8`
  - `writer_model = ""`

这说明：**Writer backend 路线本身已经形成单一执行口径。**

### 仍然存在的歧义口子

#### 口子 1：`7.8` 目前在“活配置”里已经生效，但在当天记忆里仍被表述成“本次 run 的人工放行口径”

这会带来一个典型歧义：

- 从系统执行角度看：`config.json=7.8`，那它就是当前默认阈值
- 从人工复盘角度看：记忆里又说“不是长期默认线，除非老板再次明确修改”

这两句话不能长期并存。因为你们自己已经把 `config.json` 定义成**唯一权威源**；只要它还是 7.8，系统就会按长期默认执行。

**结论：现在最大口子不是数字本身，而是“临时放行”被写进了默认活配置。**

#### 口子 2：活规则源 / 记忆源 / 偏好源 的分工还没被一句硬规则钉死

目前能看出大致分工，但还缺一个非常明确的优先级合同：

- `config.json`：机器执行阈值 / 活配置
- `AGENTS.md`：主流程行为规则
- forge `SKILL.md`：流水线合同
- `USER.md`：老板偏好 / 特殊明确偏好
- `MEMORY.md` / `memory/*.md`：历史事实、决策背景、复盘，不直接改写活配置

现在这个分工是“读得出来”，但不是“写死了”。

一旦以后有人先改 MEMORY、没改 config，就会再次出现“口头上说临时、系统里却已经默认”的问题。

#### 口子 3：`writer_model` 的空值语义虽然已一致，但仍建议合同化到“禁止 fallback 旧 backend”级别

现在规则已经写到“空则继承父级模型”，但还可以再补一句更硬的话：

- `writer_model` 为空时，**只能**意味着“omit `sessions_spawn.model`，继承父级模型”
- **不得**把空值解释成“启用历史默认 writer backend / CLI / API fallback”

这条今天看上去像废话，但它正是防止未来回潮的最小保险丝。

## 二、特别回答

## 1) 7.8 是不是应该正式落成默认阈值？

### 我的结论：**是，应该正式落成；或者立刻回滚 config。不能继续维持“config=7.8，但口头说它只是临时放行”。**

原因不是我主张 7.8 一定更优，而是从**规则源收口**角度，当前系统已经做了选择：

- 你们定义过：**唯一权威源是 `config.json.review_pass_threshold`**
- 现在 `config.json` 已经是 `7.8`

所以只要不回滚，`7.8` 在机器侧就已经是**正式默认阈值**。

换句话说，当前不能再说“系统默认线不是 7.8，只是这轮临时放过”。

### 最小可实施判断

有两个互斥选项：

#### 选项 A（我建议，最小改动）
**正式承认 7.8 已成为当前默认阈值。**

优点：
- 与现有 `config.json` 一致
- 与“单一权威源”原则一致
- 不需要额外发明回滚/例外解释
- 最容易避免下次执行时再争

适用前提：
- 今晚这次把 8.2 → 7.8，不只是纯应急放水，而是老板认可当前产品期望值已经变了

#### 选项 B（也可，但要立刻做干净）
**若老板只想保留“本轮特批”，那就必须立刻把 `config.json` 改回原默认值，并把 7.8 只记录为 run-specific override / waiver。**

优点：
- 保住原长期标准
- 临时放行与长期默认彻底分离

缺点：
- 需要马上补“单轮例外如何记”的 durable 合同
- 否则下次还会重复

### 就今晚这套现状而言，我更推荐 A：正式落成 7.8 默认阈值

原因很简单：
- 机器已经这么在跑
- 活规则源已强调 config 独占
- 现在再把它解释成“只是临时”只会制造二义性

如果未来想再抬回去，再通过一次明确的“默认阈值变更”改 config 即可。

## 2) 还需不需要再加任何硬规则，避免下次复发？

### 需要，但只需要补 2 条很小的硬规则，不要扩一大堆

#### 硬规则 A：**run 例外不得直接冒充默认配置**

建议规则文案含义如下：

- `review_pass_threshold` 的默认值只认 `config.json`
- 若某一轮 run 需要临时降线 / 特批放行，必须写成 **run-specific override / waiver**，落到当轮 durable state / artifact
- **除非老板明确决定“默认阈值永久变更”**，否则不得直接改 `config.json`

这条是防复发的第一关键规则。

因为今晚暴露的问题，本质上不是 7.8 对不对，而是：**“单轮特批”直接写进了全局默认源。**

#### 硬规则 B：**记忆文件不能改写活配置，只能记录“为什么”**

建议规则文案含义如下：

- `MEMORY.md` / `memory/*.md` 记录历史事实、决策背景、复盘解释
- 但它们**不得充当当前活规则的反向 override**
- 当 MEMORY 与 `config.json` / `AGENTS.md` / forge `SKILL.md` 不一致时，执行一律以前三者为准

这条会让“今晚临时放行，但 config 还在 7.8”这种叙述不再能长期悬空。

### 另外一条我认为值得补，但优先级略低

#### 硬规则 C：`writer_model=""` 的唯一合法解释

- 空值 = 继承父级主模型
- 不得触发任何旧 backend fallback
- 不得触发隐式默认模型字符串补写

这条是防历史残留回潮，不是为了今晚 7.8 问题本身。

## 三、最小修复方案

## Must-fix（这次就该补）

### 1. 对 `7.8` 做一次正式定性：默认值 or 单轮例外，二选一

最小要求：不能再维持现在这种“双口径”状态。

建议：
- **直接定性为当前默认阈值 = 7.8**
- 并同步把相关记忆表述改成“今晚已正式收口为 7.8 默认线”

如果不想定为默认，就反过来：
- 立刻把 `config.json` 改回原值
- 另写当轮 waiver / override 记录

**重点不是选哪边，而是必须只保留一边。**

### 2. 明确“活规则源优先级”

建议收口成一句：

1. `config.json` = 数值型活配置 / 默认阈值真源
2. `AGENTS.md` = 主 agent 行为规则真源
3. forge `SKILL.md` = 流水线合同真源
4. `USER.md` = 老板明确偏好（不与前三者冲突时生效；冲突时需显式改活规则源）
5. `MEMORY.md` / `memory/*.md` = 决策记录 / 历史上下文，不直接改写当前默认执行

这条一旦写死，后面很多争议都能直接判。

### 3. 补一条“单轮特批不得改全局默认”的硬规则

这条要么写在 AGENTS，要么写在 forge `SKILL` 的配置/评审段落，核心只要一句：

- **run-specific review override 必须走当轮 durable state，不得直接写进 `config.json`，除非明确宣布默认值变更。**

这是最值钱的一条防复发规则。

## Can-wait（可以后补，不影响今晚主收口）

### 4. 把 `writer_model` 的空值语义再合同化

补成更硬的话：
- 空值只代表继承父级模型
- 不触发任何旧 writer backend fallback

### 5. 给 run-specific override 约定一个固定字段名/落盘位置

比如以后统一写到：
- `pipeline-state.json.review_override`
- 或 `review-waiver.json`

这不是今晚必须立刻定完实现细节，但建议以后别再临场发明。

### 6. 做一次“活规则源清单”小表

把哪些文件有执行权、哪些文件只是记忆/说明，列成一个很短的表，放进 AGENTS 或某个 references 文档。不是必需，但会明显降低以后复盘时的误判成本。

## 四、我给出的最终建议版本

### 推荐定案

**把 `7.8` 正式落成当前默认阈值。**

同时补两条最小硬规则：

1. **默认阈值只认 `config.json`；单轮特批不得直接改全局默认。**
2. **MEMORY 只记录决策背景，不反向覆盖活配置。**

这样做的好处是：
- 不用回滚今晚已经对齐好的控制面
- 与“单一权威源”原则完全一致
- 下次再临时放行时，有明确的例外通道，不会再污染默认配置
